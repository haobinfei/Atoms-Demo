# ADR-0015: 构建产物按数量与时间双限保留

`/app` 的构建产物按**每个构建前缀**清理：保留**最新 20 个构建**，**永远保留当前活动构建**，
并删除**超过 30 天**的；`published` 前缀只保留活动的那一份。GC 通过给 `artifact.Backend`
加一个 `List` 方法实现枚举——这是 Go 接口扩展，不涉及任何表结构。

## 为什么需要清理

Artifact Store 把每次成功构建写成不可变目录（`builds/<buildID>/...`），但**既不枚举也不回收**：
`Backend` 接口只有 `Put` / `Get` / `Copy` / `DeletePrefix`，没有 `List`，所以旧构建只增不减。
更糟的是**每次发布还会额外留一份**：发布走 `CopyTree`（`internal/artifact/store.go:246-301`），
它把当前活动构建的文件**复制**到 `published` 前缀下的**新构建**并激活，只新增不清理——
发布 N 次就积 N 份完整副本。

## 为什么不按「发布记录」钉住

「被发布过的构建不能删」听起来像正确性约束，但它**既做不到也不需要**：

- **做不到**：`Publish` 结构只有 `version` / `url` / `at` / `unpublished`，**没有指向构建的字段**，
  所以「被发布记录引用的构建」根本无法识别。要加那个字段就得改数据模型，而本轮已明确不做
  用户可见的版本能力（`OPT-504` 不做），因此不为一个用不到的能力付数据模型的代价。
- **不需要**：发布是**独立副本**而不是指针共享。`CopyTree` 复制的是活动构建的**文件**，
  落到 `published` 前缀下的新构建，线上 `/app/<id>/` 读的是那一份。**删掉会话前缀下的旧构建
  不会打挂已发布的链接。**

## 为什么永远保留活动构建

数量与时间都是「最新的优先」，但**指针未必指向最新创建的构建**：发布与竞赛胜者复制会在
stage → activate 之间产生中间态，失败的构建还会清空指针并回退。若清理只看创建时间，
就可能把指针指向的那一个删掉，直接让预览与 `/app` 变成 404。所以活动构建**无条件保留**，
它是这套策略里唯一的硬约束。

## 20 与 30 天怎么来的

两者是**双限**，取更激进的一侧：20 个足以覆盖演示与近期回看，30 天足以覆盖
「周末做的项目下周一回来还在」。单用数量会让长期闲置的会话永久占着 20 份；
单用时间会让高频改动的会话在一天内堆出上百份。

_Avoid_：删除当前活动构建；把保留策略做成用户可见的「版本历史」（那是已决定不做的
`OPT-504`）；用发布记录判断保留什么；在没有 `List` 的情况下靠遍历对象存储前缀猜枚举。
