# ADR-0016: GitHub 连接的 token 不落库

用户连接 GitHub 后，OAuth 的 access token **不进数据库**：服务端在回调里用对称密钥加密，
写入 **HttpOnly cookie**；push 时从 cookie 解密取用。能力边界是**单向 Push**——在用户的
个人账号下新建一个私有仓库，之后可以把更新 push 到同一个仓库。**不做 Pull 回写。**

## 为什么必须持有 token

「把项目推到用户的 GitHub」意味着平台要**代表该用户**对其账号下的仓库读写。这既不能复用
本仓库现有的凭据，也不能用平台自己的身份：

- 现有 GitHub 凭据（`atoms-demo-gitops-ssh` 等）是**只读 deploy key** 与发布回写用的
  bot 身份，作用对象是本平台的两个固定仓库，权限范围与「任意用户、任意仓库」完全不同；
- 平台自身的 token 会退化成「平台代管用户仓库」，一旦泄露影响面是所有用户。

所以必须走**用户授权**：用户在 GitHub 上授权一次，平台拿到一个可撤销的、只属于他的 token。

## 为什么不落库

落库需要一个存 token 的地方——新表或新列，也就是**数据模型变更**，外加一套加密与
密钥轮换方案（密钥本身还要放在 k8s Secret 里并支持轮换）。本轮已明确尽量不动数据模型，
而这件事有更便宜的等价做法：

**加密后放 HttpOnly cookie。** 服务端用一个来自 Secret 的对称密钥加密 token 再下发；
`HttpOnly` 意味着页面脚本读不到它，因此比「存在 localStorage 由前端带上」安全；
`Secure` + `SameSite` 限制它的传输与跨站携带。撤销就是清 cookie 并在 GitHub 侧撤销授权。

代价是**换浏览器要重连**——这是可接受的取舍：它换来的是「不新增存储、不需要密钥轮换
方案、不引入一个新的泄露面」。

## 为什么不做 Pull 回写

`Pull Updates`（GitHub → 平台）看起来只是反方向的同一个动作，实际要定义**冲突与合并语义**：
GitHub 上的改动与 Agent 生成的结果是两份独立的真相，同文件冲突时谁覆盖谁、什么时候覆盖、
覆盖后是否重建、用户手改与 Agent 修改的先后关系如何表达——这些都必须先定清楚，否则
就是静默丢改动。

而本轮同时计划做 `OPT-502`（用户在工作台直接手改代码并保存），它引入的是**第二个**
「用户修改」入口。两个入口同时存在时，「谁是基础版本」这个问题会立刻变成真问题。
因此先把 Push 做扎实，Pull 留到 `OPT-502` 落地、手改语义明确之后再评估。

## 能力边界（对齐参考产品，但更诚实）

参考产品（atoms.dev）的 GitHub 连接同样**只能新建私有仓库、不能接入用户已有仓库、
不能建在组织下**，且**不是自动同步**——要手动触发。我们采用同样的边界，但把「不能做什么」
写在界面上，而不是留给用户去试。

_Avoid_：把 token 写进 Git、日志或错误信息；把 token 落库；用平台自身身份代替用户授权；
把连接做成「平台代管仓库」；在没有定义冲突语义之前做 Pull 回写；把「只能新建私有仓库」
这条限制藏起来不说。
