# ADR-0013: 用户可取消正在执行的回合

新增用户可控的「取消回合（Cancel Turn）」动作。语义：中止本回合的生成，**保留上一版产物**，
会话回到 `ready`，并**追加**一条取消事件——已发生的事件不删除。取消只在会话处于 `building`
时可用。

这个语义之所以安全，是因为回合是原子的：`internal/pipeline/pipeline.go` 的 `writeFiles`
由 `Run` 在生成全部完成之后才调用，因此中止不会留下半成品文件，上一版产物天然保留。
事件则相反，是执行中实时持久化的，所以时间线会保留已经发生的阶段——这是刻意的：用户应当
看到"做到哪一步被中止"，而不是看到一个被清空的历史。

取消实现为**持久化标志**，而非进程内的 `context.CancelFunc` 注册表。进程内取消在
`server.replicas: 1` 时可用，但有两个失效场景：取消请求可能落到并不持有该 Job 的副本；
Pod 重启后进程内状态全部丢失。持久化标志（在执行步骤之间检查）在单副本、多副本与重启
三种情况下都正确，代价是取消的响应延迟取决于步骤粒度。

取消与既有机制的区别必须明确：`崩溃恢复（Recovery）` 是系统在检测到无租约的 building
会话后自动重跑；Provider 降级是自动容错；两者都不是用户操作。取消表达的是用户意图，
不能复用它们的实现或语义。

取消与排队消息的关系：取消后，排队中的消息**保留待发**，由用户确认后再发送，不自动执行。
理由是用户取消通常意味着"这次方向不对、我要改需求"，此时队列中的消息很可能建立在旧前提上。

_Avoid_：使用"停止任务""终止任务"等说法（`任务（Job）` 已专指调度单位，见 `CONTEXT.md`）；
取消后回滚到更早的版本或删除已发生的事件；用进程内 cancel 冒充多副本可用的取消；
取消后自动执行队列中的消息；把取消当作失败（会话应回到 `ready`，不是 `failed`）。
