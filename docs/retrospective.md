# Atoms Demo 项目复盘

> 实现一个具备 Atoms 能力与交互体验的网页应用：智能体驱动的代码生成 + 可视化预览。
> 线上地址：https://atoms.ss-vip.cn

## 一、实现思路与关键取舍

核心是「把 LLM 的不确定性关进确定性的管道里」——任何时刻都要产出能跑的东西。
架构为模块化单体（Go 后端 + React 前端，分离部署），关键取舍如下。

### 1. 嵌入式 esbuild + 预置 React vendor，零网络构建

生成的应用只允许 import react/react-dom，沙箱里没有 node_modules、没有供应链风险、
构建毫秒级完成。代价是 LLM 幻觉第三方包会硬失败——用「CSS 缺失自愈」先堵住最高频的洞
（构建器扫描 esbuild 解析错误，缺失的 .css import 补空桩重试，最多 4 轮），
更完整的方案是构建失败回喂 LLM 修复（见扩展计划）。

### 2. 模型链 DeepSeek → Kimi → 本地 gemma

任何一环挂掉自动减员，剩下的继续比赛或继续服务。模型全部不可用时，回合显式失败并
把错误写入事件流；不再使用正则模板伪造成功结果。模板无法执行后续内容需求，且会掩盖
真实模型故障，因此现在只保留为测试夹具（ADR-0008）。

### 3. 文件系统即存储 + 事件溯源

每个会话一个目录：app/（源码）、dist/（构建产物）、contest/（竞赛归档）、
session.json（追加式事件流）。SSE 按 seq 重放，pod 重启、浏览器断线、
发布滚动后都能追平状态，不需要数据库。代价是聚合查询弱
（跨会话统计要扫文件）——leaderboard 必须引入独立数据模型，投票数据不适合塞进 session.json。

### 4. 预览存储按构建隔离

预览 iframe 加载时注入脚本，以构建产物时间戳作为 localStorage 命名空间：
每次重建获得全新存储视图（新默认值生效，不被旧数据遮蔽），同一次构建内的用户编辑刷新后保留。
这条语义来自两次真实故障：旧数据遮蔽新默认值导致预览「恒空」；
无缓存策略导致浏览器喂旧 bundle。取舍是用户的预览数据不跨构建存活——
对生成式工具这是正确语义，不是缺陷。

### 5. GitOps 全链路交付

push main 构建推送 sha 镜像，打 v* tag 额外回写 gitops 仓库 values.yaml，
ArgoCD automated sync 检测变更自动拉起。集群侧只需要 deploy key 和镜像仓库凭证，
服务器零手工操作。代价是发布链路长（5-8 分钟）且滚动会杀掉进行中的 SSE 连接——
前端看门狗（15s 轮询对账）兜住后者；发布慢靠构建缓存缓解，暂未做。

### 6. 平台 SDK 以构建器命名空间注入，而非写进生成 prompt

atoms-pay 支付 SDK 由 esbuild plugin 在构建时拦截 `./atomspay` import 直接供给源码，
LLM 只需知道模块导出的三个函数。比让模型自己写支付代码安全几个量级，
也比把 SDK 源码塞进上下文省 token。代价是要持续和模型的幻觉命名作斗争
（臆造不存在的导出），需要宽松解析 + 提示词加固双保险——这类注入方案的固有维护成本。

### 7. 生成异步化：任务状态永远落在执行者之外

生成与构建是重操作（LLM 调用 30-300s），绝不能放在请求路径上，也绝不相信
任何 pod 能活着跑完。当前实现（HTTP 处理器创建会话后立即返回，执行靠散养
goroutine）已具备「API 不阻塞」的性质，但缺队列纪律。目标形态的三层防线：

- **队列外置**：进程内 channel 随 pod 死亡消失；生产形态用数据库即队列
  （job 一行 `{session_id, kind, status, claim_expires_at}`，入队=INSERT，
  消费=事务性 UPDATE，与会话状态天然一致）
- **租约 + ack**：worker 执行前 CAS 抢租约（pending→running），完成清租约；
  pod 中途死亡 → 租约过期 → 任务重新可见。交付语义 at-least-once，
  靠「job 只带会话指针 + 执行前校验会话处于合法状态」把重复投递变成无害空转
- **sweeper 兜底**：定期扫描「building 且无活人租约」的会话重新入队——
  会话状态是事实源，队列只是加速器，broker 丢了也能从状态完整重建待办集

关键取舍：重执行不可消除（pod 死在生成中途就要再付一次 LLM 调用、
产出不同代码），用粗粒度 checkpoint 缓解——生成产物立即落盘，
重跑时产物完整则跳过生成直接构建；租约时长在「丢任务等待时间」和
「重复执行概率」之间调参。设计原则一句话：pod 是随时会死的牛，
不丢任务的防线不是「pod 不死」，而是「任何执行者死后有人能从状态重建队列」。

### 8. 鉴权与租户：能跑的临时方案，刻意不设计

当前实现是把 AuthSphere OIDC 当黑盒用：中间件校验 JWT、取 subject
作为用户 ID，会话按 owner 目录物理隔离，另留 DevAuth 直通开关给本地开发。
租户概念为零——没有组织/团队、没有角色、没有配额、没有 API Key，
「多用户」等于「多个并列的个人空间」。

这是有意的临时方案：产品形态未定时先买标准件（OIDC 协议 + 外部
IdP），把「谁是自己人」这件事外包，换来零账户系统维护成本。
代价是管理面完全缺位——无法做按租户的资源隔离与计费、无法授权
服务间调用、管理员能力为零，且 DevAuth 直通绝不能带进生产配置。
后续需要独立设计：租户模型（org/workspace 两级）、配额与计量、
API Key 体系、以及与异步化队列（P0）的优先级衔接——配额要在
队列入口限流才有意义，先于它做是空转。

- 双 LLM 竞赛模式：同一 prompt 由 DeepSeek 与 Kimi 并行生成，Nina 三维度评审
  （LLM 评分 + 启发式兜底），人工点选胜者，败者版本归档可回看
- 版本化发布（/app/{id}/ 公开快照，支持多次发布）
- 模拟支付闭环（atoms-pay SDK 注入 + 下单/收银台/支付回调/订单列表）
- OIDC 登录（AuthSphere 集成）、多项目管理（看板/置顶/导出 zip）
- 预览自愈体系：响应级 no-cache + 按构建隔离 localStorage + 15s 前端看门狗

### 明确未做

- 生成异步化（取舍第 7 条 / P0）：当前执行仍是进程内散养 goroutine——
  无队列、无 worker 池、无 LLM 并发闸门；pod 重启靠启动扫描恢复，
  进程内任务随 pod 死亡即丢失（会话状态可重建，执行中断不可续）
- 模型竞技场的数据层（盲测投票、Elo、leaderboard 仅有设计，未实现）
- LLM 构建修复回合（构建失败仅 CSS 类可自愈）
- 数据库（投票/排行数据无处沉淀）
- Nina 裁判与参赛者未解耦（存在「运动员兼裁判」）
- 匿名访问与公开投票页、真实支付
- 鉴权与租户的独立设计（当前 AuthSphere OIDC + owner 目录隔离是
  临时方案，见取舍第 8 条；组织/角色/配额/API Key/管理面均未做）
- 构建失败路径的端到端测试覆盖不全

## 三、扩展计划与优先级

### P0 生成异步化：队列化 + 任务不丢（弹性最大的单点改造）

把散养 goroutine 升级为有纪律的队列系统（见取舍第 7 条）。分两步：

- **Stage 1（进程内队列）**：`internal/queue` 接口 + channel 实现，
  worker 池按会话串行（单 dispatcher + 每会话互斥锁），worker 池大小
  即 LLM 并发闸门（加 per-provider 信号量防打爆 RPM）；启动时扫描
  status=building 会话重入队（崩溃恢复）。API 与执行解耦，重启自愈。
- **Stage 2（外置队列 + 多副本）**：接口换 NATS/Redis 实现，
  store 加 Claim/Release/Sweep 租约语义，KEDA 按队列深度扩 worker。
  前置条件：workspace 共享存储（ReadWriteMany PV 或对象存储）、
  SSE broker 改从事件存储推（跨副本）。

为什么排最前：它是所有后续扩展（竞技场数据沉淀、多租户配额、计费）
的执行底座——没有队列纪律，并发失控和丢任务会先杀死口碑；
且改动不动领域模型，store 层已有锁和事件 seq，落地成本低。

### P1 模型竞技场（差异化叙事核心）

同一 prompt 由两个模型同时生成，用户盲测投票（A/B/平局，身份投后揭示），
沉淀 Elo/Bradley-Terry 排行榜。复用度最高：竞赛编排、双预览归档、SSE 事件流
都是现成积木，新增仅为 battle/vote/rating 三个数据模型 + 盲测 UI。
差异化：atoms.dev 没有公开模型对比叙事，LMArena 不评「生成可用应用的质量」。

关键技术点：归档 URL 需别名化防泄身份（当前路径含 provider 名）；
左右位置按 viewer 随机抹平位置偏差；登录用户一人一投（OIDC 已有）。

### P2 生成质量闭环

- 构建失败回喂 LLM 修复（1-2 轮），覆盖所有失败类别（幻觉包/漏文件/语法错）
- Nina 评分用非参赛者模型（kimi 参赛则 deepseek 当裁判），消除利益冲突
- 共享 node_modules 预热 + 按需安装（热路径零网络，长尾包一次安装进缓存），
  把「零网络」从硬约束降级为「热路径零网络」，幻觉失败率趋近于零

### P3 生态化（依赖 P1 数据量）

接入新模型即入榜、按 prompt 主题分类排行、对战回放页、数据导出（博客素材）。
提前做是空转。

### P4 产品化（看增长信号）

鉴权与租户独立设计（取舍第 8 条：org/workspace 两级租户模型、
配额与计量、API Key 体系、管理面）——注意它与 P0 队列化的衔接：
配额限流要拦在队列入口，应在队列之后落地；真实支付、匿名投票限流页。
当前阶段做是过度工程。

## 四、一句话总结

「能跑、能玩、能扩展」已达成：竞赛模式跑通双真模型对打，kimi 与 deepseek 质量相当。
下一步先用队列化把执行面铸成「任务不丢、并发有闸、死亡自愈」的底座，
再把已有对打从「明牌评审」升级为「盲测沉淀」——让每一场竞赛都变成
leaderboard 上的一个数据点。
