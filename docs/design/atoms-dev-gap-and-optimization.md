## 3. 六维差距与优化项

### 3.1 注册登录（3/5）

现状：认证链路完整（注册、验证、登录、忘记/重置密码、会话吊销）。缺口在**进入产品的顺畅度**与**首次使用引导**。

- `OPT-101` 表单体验：密码显隐切换、输入时密码规则提示（当前仅靠 `minLength=12`）、字段级错误提示、验证邮件重发倒计时。证据：`web/src/Auth.tsx:122-129`。
- `OPT-102` 登录后回到原位置：会话过期跳登录后，重新登录应回到原项目而非首页。证据：`web/src/api.ts:211`（`redirectToLogin` 直接 `location.href = '/'`）。
- `OPT-103` 注册后引导：注册完成提供示例需求或模板，帮助用户产出第一个应用。
- `OPT-104` 第三方登录（OAuth）：Atoms 支持邮箱密码与 Google 等。**本轮不做**（§8.1 依赖政策）。

### 3.2 Agent 交互（3/5）

现状：多 Agent 人设、阶段事件、文件事件、追问均已实现。缺口在**过程可读性**与**用户控制权**。

- `OPT-201` 时间线卡片化：当前事件逐条平铺，同 Agent 连续事件用表头合并。改为按**回合（Turn）**分组，显示"本轮目标 → 执行过程 → 交付结果"。证据：`web/src/Timeline.tsx:24-63`。
- `OPT-202` 文件事件折叠：`file` 事件逐条展示路径，改为"修改了 N 个文件"可展开。证据：`web/src/Timeline.tsx:52`。
- `OPT-203` 回合完成摘要：流水线已写入回合摘要消息，前端未突出展示。证据：`internal/pipeline/pipeline.go:224`（`appendTurnSummary`）。
- `OPT-204` 失败可诊断：当前 `error` 事件只展示 `err.Error()`，缺少失败阶段与可执行建议。证据：`internal/pipeline/pipeline.go:176`。
- `OPT-205` 追问排队：构建中输入框被禁用，用户无法预先输入下一条。Atoms 支持排队并可编辑/删除/重排。**已定：纯前端内存队列**（§8.1），构建中可继续输入，回合结束后自动发送；刷新丢失，可接受。
- `OPT-206` 取消正在执行的回合：无任何后端取消路径。**已定：术语「取消回合（Cancel Turn）」，实现为持久化标志**（§8.1）。语义见 §8.1 与 `docs/adr/0013`。
- `OPT-207` 用户主动重试失败回合：现有"重跑"只有崩溃恢复（`recovery`）与 Provider 降级，二者都不是用户操作。证据：`docs/adr/0007`、`internal/provider/chain.go:31`。

### 3.3 数据持久化（3/5）

现状：Postgres 为事实源，会话/事件/消息/发布记录已落库；事件有跨副本分发与断线重放。缺口在**可靠性可验证**与**源码/产物持久化边界**。

- `OPT-301` 可靠性验收清单：刷新、断网重连、服务重启三种情况下，项目列表、消息历史、构建状态必须一致。**这是"提分证据"而非新功能。** —— **已完成**（工单 #57）：空闲重启与运行中重启两个场景实证通过，方法与结果见 §11.1；崩溃恢复的可用性延迟登记为后续工单（§11.5）。
- `OPT-302` 源码持久化边界：数据库存元数据，生成源码仍在 workspace；多副本需共享 RWX 存储。需核验正式环境实际配置（COS / Redis / 共享卷）。证据：`README.md:60`、`cmd/server/main.go:112`。 —— **已完成**（工单 #57）：正式环境核验结论（replicas=1、RWO 节点本地卷、无 RWX StorageClass）与扩副本前置条件见 §11.2。
- `OPT-303` 生成应用的业务数据持久化：平台保存项目 ≠ 生成应用保存业务数据，演示时须分别验证（例：待办应用写入一条数据 → 刷新 → 重新登录 → 数据仍在）。 —— **已处置**：两条已知取舍（重建即重置、换设备看不到）写入说明与演示话术，见 §11.4 与 §6.1 步骤 9–11。
- `OPT-304` 构建历史保留与 GC：当前旧 build 无限累积且不可枚举。若要做版本能力，需先加 List 与清理策略。**本轮范围外**；启用前需先解决 §5 第 1 项的「版本」定名。

### 3.4 页面美观度（2/5）

现状：上一轮 P0 已落地设计 token、统一组件类、深色设计系统、认证页品牌栏、账户菜单、项目卡片。缺口在**用户停留最久的工作台**。

- `OPT-401` 工作台布局：聊天与预览比例固定，改为**固定比例 + 可折叠**（放大预览 / 放大对话切换）。**已定**（§8.1）；不做拖拽分栏与宽度持久化。
- `OPT-402` 视觉层级：统一 Agent 消息、工具活动、完成摘要、失败状态的层级，替换当前平铺样式。
- `OPT-403` 输入体验：输入框改多行，`Enter` 发送 / `Shift+Enter` 换行。证据：`web/src/Workspace.tsx:183`（当前为单行 `input`）。
- `OPT-404` 状态反馈：补齐加载、空、断线、失败四态的明确反馈。
- `OPT-405` 项目封面改用截图缩略图：当前每张 ready 卡片加载一个真实 iframe，列表变大后并发运行多个应用。**已定：本轮不做缩略图，保留实时 iframe 并加并发上限**（§8.1）。方案背景见 `docs/design/ui-refresh-p0.md` §4。

### 3.5 代码管理（3/5）

现状：文件列表、源码读取、复制、ZIP 导出已实现。缺口在**编辑**与**改动可追溯**。**本轮不做。**

- `OPT-501` 文件树增强：文件名搜索、语法高亮、行号。当前为纯文本列表 + `<pre>`。证据：`web/src/FilesDrawer.tsx:74-81`。
- `OPT-502` 代码编辑与保存：需要后端写入路由（当前只有 list/read/export，**没有写入接口**）。证据：`internal/server/server.go:365-367`。
- `OPT-503` 改动对比（Diff）：Atoms 支持逐文件 Diff。需要保存编辑前后版本。
- `OPT-504` 版本历史与恢复：见 §3.6 与 §5 第 1 项，成本最高。
- `OPT-505` GitHub 同步：Atoms 支持导出并同步到 GitHub。**本轮不做**（第 5 项不在本轮范围）。

### 3.6 产物预览（3/5）

现状：桌面/移动视口、刷新、新标签页、竞赛候选回看均已实现。缺口在**稳定性**与**失败可诊断**。

- `OPT-601` 修复预览周期性重载：见 §4 BUG-1。**优先级最高。**
- `OPT-602` 修复竞赛候选预览的"打开"链接：见 §4 BUG-2。
- `OPT-603` 预览加载与失败状态：当前 iframe 无 loading/error 反馈。
- `OPT-604` 预览可用性检测：`iframe.onError` 无法识别跨文档 HTTP 错误页。**已定：服务端派生标志 `previewReady` + 前端加载超时兜底**（§8.1、`docs/adr/0014`）。
- `OPT-605` 草稿版与已发布版标识：让用户分清正在看的是预览还是线上版本。
- `OPT-606` 生成应用与平台的权限隔离：`/app` 与 SPA 同源，README 明确当前同源路由**不是**已验收的生产权限边界。证据：`README.md:94`、`docs/adr/0010`。**本轮范围外。**

## 4. 可直接修复的确定性缺陷

这四条是代码级事实，不依赖 §8 的任何决策，可独立修复。

### BUG-1 预览周期性重载（高优先级）

`web/src/Workspace.tsx:82-98` 的 15 秒对账在 `status === 'ready'` 时仍执行 `setBuiltAt(new Date().toISOString())`（L94）。`builtAt` 是 `Preview` 的 iframe key 组成部分（`web/src/Preview.tsx:48`），因此**只要会话处于 ready，预览每 15 秒被强制重载一次，用户无法在预览里连续操作**。

修复方向：只在构建版本实际变化时更新 `builtAt`（例如比较构建标识或 `updatedAt`），对账只用于补齐事件与状态。

### BUG-2 竞赛候选预览的新标签页链接错误

`web/src/Preview.tsx:41` 的"打开"链接固定为 `/app/${sessionId}/`。当 `src` 被指定为竞赛候选版本（`web/src/Workspace.tsx:231` 传入 `/app/{id}/contest/{provider}/`）时，新标签页打开的仍是正式版而非当前正在看的候选版本。

修复方向：`打开` 链接与 iframe 使用同一个 `src`。

### BUG-3 发布等待超时

`web/src/api.ts:230-244` 的 `publishSession` 轮询 15 秒后抛错。发布实际由 Worker 异步执行（`internal/server/server.go` 的 publish 任务），构建较慢时会稳定超时，前端只显示"操作失败，请稍后重试"，用户无法判断是否已成功。

修复方向：改为订阅已有的事件流或延长轮询并展示进行中状态，不要用固定超时判定失败。

### BUG-4 iframe 错误检测不可靠

`web/src/Dashboard.tsx:45` 依赖 `iframe.onError` 触发降级封面。跨文档的 HTTP 错误页（如 404/502 返回 HTML）不会触发 `onError`，因此降级逻辑会漏判。

修复方向：已定为由服务端派生标志 `previewReady` 判定（由 `status` 与 `current.json` 计算，不落库），前端仅在为真时渲染 iframe，并叠加加载超时兜底。详见 §8.1 与 `docs/adr/0014`。**注意该标志只是渲染提示，不得当作权限判据。**

## 5. 术语冲突

`CONTEXT.md` 是本仓库的术语表，`docs/agents/domain.md` 要求输出必须使用其中词汇。以下三处曾存在冲突，现状如下：

1. **"版本"被三种概念混用**（**未定名**）：`发布（Publish）` 的版本号（`session.go:85` 的 `Version`）、内部的 `buildID`（`artifact/store.go:344`）、以及竞赛归档版本（`contest/<provider>`）。`CONTEXT.md` 里 `发布` 写着"发布记录是版本事实"，但发布记录**不含 buildID**，三者当前无法互相定位。**处置：本轮不定名，但新增文案与字段命名中避免使用"版本"一词**（见 §8.1），等做版本历史时再定名并写 ADR。
2. **用户态"停止任务"与 `任务（Job）` 撞名**（**已解决**）：`CONTEXT.md` 明确"任务"专指调度单位（`turn`/`contest`/`publish`），并注明"勿与「回合」混用"。**已定名为「取消回合（Cancel Turn）」**，不得使用"停止任务""终止任务"等说法（见 §8.1）。
3. **缩略图与 `预览` 的边界**（**本轮不触发**）：`CONTEXT.md` 定义 `预览` 为"工作区成员检查未发布应用的运行结果的访问方式；非成员不能访问"。未发布应用的缩略图属于该边界内，**不得作为公开资源**；且 `项目（Project）` 被定义为列表项展示层，加 `thumbnailUrl` 是对该模型的变更，需同步更新术语表。**处置：本轮不做缩略图**（见 §8.1），该冲突暂不触发；未来若启用，必须先解决本项。

### 10.3 本轮新核实的事实（推翻了先前的判断）

1. **发布是独立副本，不是指针共享。** `artifact.CopyTree`（`internal/artifact/store.go:246-301`）只复制**活动构建**的文件，写入 `published` 前缀下的**新构建**并激活。因此 **GC 旧构建不会打挂已发布的线上链接**——先前「被发布过的构建必须钉住」的判断不成立，而该判断本来也不可实现（`Publish` 结构无 buildID）。
2. **每次发布都会在 `published` 前缀下留一份新副本**（`internal/server/server.go:1427` 只新增不清理）。发布 N 次积 N 份，属于真实堆积，归 `OPT-304` 一并处理。
3. **生成应用的数据只在浏览器 localStorage**（`internal/provider/template_apps.go:30-35`、`template_site.go:36-43`，`internal/provider/llm.go:20` 的 prompt 也要求如此）。服务端在 `index.html` 里注入一段脚本，**透明地给 localStorage 加上「按构建」的命名空间前缀**（`internal/server/server.go:730-745`），应用代码不用改。因此：① 换设备数据丢失；② **每次重建后数据重置**（刻意设计：防止早期写入盖掉新构建的默认数据）。唯一落库的业务数据是模拟支付订单。先前「同一浏览器上不同账号串数据」的说法**说重了**——能共享的前提是两人已能访问同一个应用且在同一浏览器，不是安全漏洞。
4. **atoms.dev 的 Git 集成只有 GitHub**（官方集成目录 `help.atoms.dev/en/articles/12129568-integrations` 源码管理仅列 GitHub；`/12129569-connect-github` 写明走 **GitHub OAuth App**，scope `repo`/`read:user`/`workflow`，**只能新建私有仓库、不能接入已有仓库、不能建在组织下**，**手动 Push/Pull 不是自动同步**，需付费计划且仅工作区所有者可连）。**未找到任何 GitLab 依据**（changelog 页抓取为空，故不能完全排除，但无依据）。集群内**没有**任何自建 Git 服务。
5. **集群已有 `OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET`**（`atoms-demo-env` 键名），但**既未注入 Deployment，代码也不读**（`ADR-0005` 已被 0009/0010 取代）。所以第三方登录不是「缺凭据」而是「有壳无核」——本轮仍不做。
6. **`sessions.publishes` 是 `JSONB`**（`deploy/local/01-baseline.sql:16`），给 `Publish` 加字段**不需要任何 DDL**。本轮既然不做 `OPT-504`，这条只作为将来参考。
7. **DNS 泛解析已存在**（`*.ss-vip.cn → 47.94.97.190`），但全集群证书均为单域名、无通配符；`letsencrypt-prod` ClusterIssuer 可用。独立域隔离卡的是「证书 + Gateway listener」，不是 DNS。

## 11. 可靠性与持久化边界走查记录（工单 #57，2026-10-15）

本节是 C 包收尾项 `OPT-301` / `OPT-302` / `OPT-303` 的**实证记录**。验证用的 harness 与脚本是本地临时设施（`cmd/restartcheck/` + `/tmp/restart-verify*.sh`，**按 §7 不提交**），装配与口径记录如下，可随时重建复跑。

### 11.1 实例重启一致性验证（`OPT-301`，已完成）

**方法**：生产装配（PGStore + Redis Streams 队列 + FanoutBus + DevAuth）起在 127.0.0.1:4188，经 HTTP 驱动真实进程重启。隔离环境：Postgres `atoms_identity` 库内独立 schema `atoms_restart`（4 张基线表，TRUNCATE 后开跑）；Redis **DB 2**（与生产的 DB 1 隔离，原因见 11.3）。两个场景各跑一次完整流程：

| 场景 | 操作 | 通过标准 |
| --- | --- | --- |
| 空闲重启 | 两回合后会话就绪，SIGKILL，重启 | 重启前后 11 项字段完全一致；重启后新回合正常追加 |
| 运行中重启 | 第二回合执行中（`building` 且 `started_at` 已置位）SIGKILL，重启 | 恢复路径走通且无状态损坏（见下） |

对比口径（重启前后各拉一份快照逐项比对）：`status`、消息数、事件数、文件数、`src/App.tsx` 字节数与 SHA、`/app/{id}/` HTTP 码与 index.html SHA、改动记录数、SSE 重放条数。

**结果**：

- **空闲重启 PASS**：11 项字段全部一致（`changed across restart: {}`）；重启后新回合正常追加（消息 4→6、事件 17→26、改动记录 8→12），`/app` 仍返回 200。
- **运行中重启 PASS**：恢复路径为「死者租约过期 → sweeper 重排队（日志可见 `recovery sweep: re-enqueued`）→ worker 从头重跑该回合」。恢复后：会话 `ready`、`/app` 200、文件数不变；**用户消息不重复**（2→2，入队前已落库）、**恰好追加一条回合摘要**（1→2，摘要在完成时落库）；中断前已写入的事件保留、重跑事件续接，事件 9→19、改动记录 4→8 单调增长；恢复后再发一个回合完全正常（消息 4→6、事件 19→28）。
- **结论**：Postgres（事实源）+ 工作区文件 + Redis（队列/扇出）三分工下，进程级重启——包括回合执行中被杀——不丢状态、不坏产物、不重复消息。可用性延迟的边界见 11.5 登记项 1。

### 11.2 生成源码的多副本边界（`OPT-302`，结论）

现状证据（2026-10-15 实测）：

- `gitops/charts/atoms-demo/values.yaml`：`server.replicas: 1`；线上 Deployment `atoms-demo-server` 为 `1/1`。
- workspace 卷（`atoms-demo-workspace` 与 identity 的 claim）均为 `ReadWriteOnce` + `local-path`（rancher.io/local-path，**节点本地存储**，WaitForFirstConsumer）。
- 集群仅一个节点（`haobinfei-x99`，k3s control-plane）；StorageClass 只有 `local-path` 与三个 hostpath（no-provisioner），**没有任何 RWX 能力**；PV 带指向唯一节点的亲和。

**结论**：

1. **数据面可多副本**：会话/事件/消息/发布在 Postgres（事实源），队列与实时扇出在 Redis，跨副本共享（ADR-0007）——这部分设计上已经就位。
2. **文件面不可多副本**：生成源码、`dist/`、`changes.jsonl`、`thumbnail.png` 都在节点本地 RWO 卷上。第二个副本调度到其他节点**挂不上**该卷；即便同节点挂上，两个 worker 同时操作同一会话目录仍是正确性风险（每会话认领租约只串行化*执行*，不锁*文件*）。
3. **前置条件（按成本排序）**：① 保持 `replicas: 1`，HA = 同节点 Pod 重启（PV 节点亲和天然满足）+ 队列崩溃恢复（11.1 已验证）；② 增加节点并提供 RWX StorageClass（NFS/CephFS 等）；③ 工作区整体迁对象存储（COS）——artifact store 已用 current 指针解耦发布产物，把 workspace 对象存储化即可让副本完全无状态。
4. 单副本的可用性缺口：Pod 是可用性单点（**数据不丢**，但重启期间不可用）。要消除该缺口必须走 ② 或 ③；在做到之前，演示与验收话术中不得暗示"多副本高可用"。

### 11.3 本地验证必须隔离 Redis DB（运营注意事项）

生产 server 的 chart 值 `REDIS_DB: "1"`（`values.yaml` 的 `server.env`）。本地 harness 若也用 DB 1，**生产 Pod 的 worker 会抢走本地入队的作业**：作业里是本地 schema 的会话，生产库（`atoms` 库）Load 不到，命中 `handleJob` 的 "session deleted" 分支被静默 ack 丢弃。症状：本地创建的会话长时间停在 `building`，直到 sweeper 按 `defaultClaimTTL`（2 分钟）+ tick（30 秒）重排队，才碰巧被本地 worker 赢回 race——首次重启校验就曾因此拖到 2 分钟以上。**对策：本地 harness 用独立 Redis DB（本次 DB 2）+ 独立 schema（`atoms_restart`）**。这是 homelab 的隔离边界而非产品缺陷，但任何在本地跑生产装配的人都必须知道。

### 11.4 两条已知取舍（`OPT-303` 处置：写入说明与演示话术）

1. **每次重建后，生成应用内的数据会重置**：生成应用的业务数据只存在于浏览器 localStorage；服务端给 localStorage 加「按构建」命名空间前缀（`internal/server/server.go` 注入），**这是刻意设计**——防止早期写入盖掉新构建的默认数据。演示时不得在一个应用里写入数据 → 重建 → 期待数据还在。
2. **换设备看不到之前的数据**：平台持久化的是项目源码与历史（Postgres + workspace），**不是**生成应用的运行时数据；换浏览器/设备后应用数据从零开始。唯一落库的业务数据是模拟支付订单。

两条已同步写入 §6.1 演示验收脚本（步骤 9–11），演示者须主动说明，避免被当成缺陷。
